## Goal for today
Find out why the headset froze ("not responding") right after pressing Enter VR, and fix it.

## What we did
Times come from the Meta Link log and our own timing log.

1. **1:56 to 2:07 pm: four tries in VR.** Each time, the headset froze after Enter VR. The Link log showed the cable was fine: it streamed at 72 frames a second and its USB check passed. The problem was that Chrome wasn't sending pictures.
2. **2:08 pm: moved Chrome to the NVIDIA graphics chip.** The laptop has two graphics chips. Chrome was drawing on the weak Intel one while Link uses the NVIDIA one. We set Chrome to "High performance" in Windows' graphics settings. Chrome moved to the NVIDIA chip, but the freeze stayed.
3. **2:16 pm: added a timing log.** The page now reports each step of starting VR to the PC program, which writes it to `vr_debug.log`.
4. **Removed the see-through attempt.** The page used to ask for the headset's see-through cameras first. Link never gives those to a PC web page, so now it asks for plain VR only.
5. **2:19 and 2:23 pm: the log found the slow part.** Asking Chrome for a VR session took 33 seconds both times. Our own setup took 30 ms. After that the page got 0 pictures from the headset.
6. **Made a tiny test page** (`vr_check.html`). It has no 3D model, camera, or safety code. It only paints the headset blue and green. It worked, so Chrome can draw to the headset over the cable, and the problem had to be in our page.
7. **2:28 pm: switched the page to WebGL 1**, the same graphics mode the test page uses. With our version of three.js, this hands pictures to the headset the older, simpler way. We also stopped Enter VR from starting twice if you click it again while it's loading.
8. **2:30 pm: the VR view works.** The camera window and 3D twin show in the headset at about 70 frames a second.
9. **2:45 pm: started `vr_teleop.py --live`.** A new `--slow` option caps the arm at 50 mm/s for the first live test (`run_live_slow.ps1` starts it).

## Results
**Worked on the real hardware:**
- The VR view (camera window, 3D twin, controller ghosts) shows in the Quest Pro over the Link cable. It runs at about 70 frames a second, and each frame takes under 1 ms of work.
- The blue and green test page (`vr_check.html`) shows in the headset.
- The camera picture in VR stays at 30 frames a second.

**Didn't work:**
- Controller buzz. Chrome says vibration is "unavailable" for both controllers over Link. So the alarm buzz, the "not now" ticks, and the force-feedback buzz don't work right now.
- Enter VR still takes about 33 seconds to start, every time.

**Not tested yet:**
- Moving the real arm with today's version. The program was started with `--live`, but we didn't write down whether the arm moved. (fill in)
- The HUD landing ring and camera calibration on the real arm

## Problems and fixes
| Problem | Cause | Fix |
|---|---|---|
| Headset showed Chrome as "not responding" after Enter VR, and the page got no pictures | With WebGL 2, three.js uses a newer way to hand pictures to the headset, and Chrome over Link never delivered frames that way | Switched the page to WebGL 1, like the working test page. We also undid one of our own changes at the same time, so we can't be fully sure which one did it, but the test page points to WebGL 1. |
| Chrome drew on the Intel chip while Link used NVIDIA | Windows lets each app pick a graphics chip, and Chrome picked the power-saving one | Set Chrome to "High performance" in Windows graphics settings. It didn't fix the freeze by itself. |
| Enter VR takes 33 seconds | Not sure. Every time, Meta's hand-tracking plugin fails to load inside Chrome, about 11 seconds apart. | Not fixed yet |
| Clicking Enter VR again while it loaded gave an error | A second request started while the first was still going | The button is turned off while VR starts |
| No controller buzz | Chrome over Link doesn't offer vibration | Not fixed yet |

## Key idea
When something freezes, measure each step before guessing. We guessed the cable, the graphics chip, the see-through cameras, the depth view, and saved files, and none of those was it. The timing log showed our own code took 30 ms and Chrome took 33 seconds. Then a tiny test page that did only the basics worked. That split the problem in half: it had to be something our page did differently, and the difference was the graphics mode.
