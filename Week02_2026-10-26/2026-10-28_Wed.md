# 2026-10-28 (Wed): Mac setup, arm connection, and working D435 capture

**Who was there:** Not recorded.
**Time spent:** Not recorded.

## Goal for today
Install the teleop dependencies on the Mac, connect to the arm, and get the camera and teleop app running.

## What we did
1. Pulled `main` to `9548b27` and reviewed the latest Windows connection notes.
2. Created `~/venvs/xarm` with Python 3.12.13. Installed NumPy 2.5.4, xArm SDK 1.18.4, OpenCV headless 5.0.0.93, Pillow 13.0.0, and `pyrealsense2-macosx` 2.56.5. Package checks found no broken dependencies.
3. Set the connected USB Ethernet adapter (`en11`, service `USB 10/100/1G/2.5G LAN`) to `192.168.1.100 / 255.255.255.0`, with no router. The arm at `192.168.1.217` became reachable. Wi-Fi settings were not changed.
4. Read the real arm's state and settings. It reported error 31, a collision/current fault, and state 4 (stopped). The refreshed settings matched the notebook: payload 0.82 kg, tool length 172 mm, collision sensitivity 3.
5. Cleared the latched fault while explicitly keeping the arm in state 4. The final read reported error 0 and state 4. No motion-enable or position commands were sent.
6. Tried the D435. It appeared on USB and the Python wrapper imported, but camera access failed with `failed to set power state`. Crash reports pointed into libusb. With Patrick's approval, ran camera-only administrator probes through the native macOS prompt. One attempt opened the pipeline but received no frames; other attempts reported `No device connected`. Later USB checks did not list the D435. Reconnection and a test with Homebrew's newer USB library did not establish working capture.
7. Started a temporary camera-disabled dry run. The page, status endpoint, VR test page, JavaScript, and robot mesh all returned HTTP 200. Status confirmed `live: false` and motion off. This did not verify headset rendering on the Mac.
8. Began a camera-worker draft to isolate driver crashes from robot control. It is unfinished and was parked in this week's code folder when Patrick asked to pause. Its temporary integration into the working teleop program was removed.
9. Stopped the dry-run server and finished progress notes when Patrick asked to pause.
10. Resumed after Patrick reconnected the camera. It stayed visible as an Intel RealSense D435, firmware 5.17.0.10, USB 2.1. The previous 640×360 color request failed because that mode was absent from the reported profiles.
11. A camera-only administrator probe at 640×480 and 15 fps received color and aligned depth frames. The last frame contained 97,707 valid depth pixels out of 307,200. Earlier failed probes remain saved separately.
12. Integrated the separate Mac camera worker into the existing Week 1 app. macOS uses the verified settings; Windows keeps its previous capture path. Only the camera worker receives administrator access. The worker script is staged outside Documents to avoid macOS denying the privileged process access to the project folder.
13. Started the integrated app in dry-run mode. Color and depth endpoints returned correctly sized 640×480 RGB pictures. Six samples over ten seconds advanced from frame 799 to 950, measured at 15.0 fps. Status confirmed `live: false` and `motion: false`; process inspection confirmed the web/control process remained under the normal user account.
14. Rechecked the arm on resuming: error 0, state 4 (stopped). No movement commands were sent. Opened the page in Codex; later inspection verified the camera view and 3D preview on the desktop.
15. Investigated controller input on the Mac. The Quest was visible on USB, but Android's device list was empty. Installed Android Platform Tools 37.0.1 and Meta Quest Developer Hub 6.5.2. Opened Developer Hub and its existing-account sign-in flow; login and headset authorization were not confirmed.
16. Added a helper for the planned Quest Browser connection over USB and five hardware-free tests. It refuses non-Quest devices and live-mode servers, maps only port 8000, and asks Quest Browser to open the page. Changed the page's Mac instructions and added left/right tracking indicators. No real controller messages were received.
17. Paused at Patrick's request. Stopped the camera dry run and verified that its web server and camera helper exited, port 8000 was free, and its temporary folder was removed. Saved resume instructions in the [Quest USB notes](code/quest_usb/README.md). Developer Hub remains at the browser sign-in handoff. Prepared this work for commit and push on `codex/macos-camera-startup`.

## Results
**Worked on the real hardware:**
- Mac-to-arm Ethernet connection and read-only SDK queries.
- Clearing the arm's latched collision/current error while keeping it stopped: final error 0, state 4.
- D435 color and aligned depth capture after reconnection: 640×480 at 15 fps, including delivery through the running teleop app.

**Worked on the computer only:**
- Python environment and required teleop imports.
- Final verification: the main suite ran 58 tests, with 57 passing and the Windows-only browser test skipped. The nine camera-worker and five Quest USB tests also passed: **72 tests total, 71 passed, one skipped**. Changed documentation had no broken local links, and Git's whitespace check passed.
- HTTP server, static resources, live color and depth pictures in dry run.
- Nine camera-worker tests passed with private local socket access, including process crash and disconnect after a valid frame. The earlier socket-permission failure was resolved by running the tests with local socket access.
- Five Quest USB helper tests passed without hardware access. The updated desktop page displayed the Mac connection instructions, camera view, and 3D preview in Codex's browser.
- Pausing closed the real camera helper and web server and removed its private temporary directory.

**Didn't work:**
- Earlier D435 attempts failed with power-state errors, a native cleanup crash, or no USB device. The resumed test succeeded after reconnection and switching to a supported stream mode; the cause of every earlier symptom was not established.
- Earlier automated Chrome inspection was blocked by tool host-access policy. Later inspection in Codex's browser verified the desktop page, not immersive VR.
- Quest controller connection on the Mac: USB device visible, but no ADB device was listed. Setup stopped at Meta account sign-in; the full reason for the missing developer connection was not established.

**Not tested yet:**
- Robot motion with this setup or the latest teleop changes.
- VR rendering and controller inputs on the Mac.
- Real camera unplug/crash behavior. Generated-frame tests cover worker failure containment; normal shutdown was verified.
- Real Quest USB port mapping, browser launch, VR rendering, tracking indicators, and controller button input.

## Problems and fixes
| Problem | Cause | Fix |
|---|---|---|
| Arm IP initially went through Wi-Fi | Ethernet adapter had a self-assigned `169.254.x.x` address | Applied the notebook's manual Ethernet address; connection worked |
| Arm reported error 31 | Controller reported a collision/current fault; its physical cause was not established | Cleared the latch while keeping state 4; final error 0 |
| D435 old stream request could not resolve | USB 2.1 connection did not offer 640×360 color | Used the reported 640×480, 15 fps color/depth mode; capture verified after reconnection |
| Earlier power-state errors, native crash, and missing device | Full cause not established | Retained failed diagnostic output; successful capture does not prove every earlier failure had the same cause |
| Camera driver could crash the main process | Native camera SDK ran inside the teleop process | Isolated the Mac driver in a camera-only worker; integrated capture verified, generated-frame failure tests passed |
| Quest plugged in, but no controller input | USB enumeration worked; the developer connection did not appear in ADB | Installed USB tools and Developer Hub; account sign-in and headset approval remain |
